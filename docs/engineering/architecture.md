# Simulation architecture and native ownership

## Arch ECS and jobs

Breakout uses **Arch 2.1.0** through `CrushKit.Brutal.Ecs`, with `ZeroAllocJobScheduler 1.1.2` for explicit dependencies. `CrushKit.Brutal.Physics` owns the reusable Box2D worker/task bridge; neither package knows about balls, bricks, catch rules or game JSON. Breakout owns those components/systems, the native arena layout, tick graph and immutable render publications.

`Config/execution.json` is required for gameplay, copied into the executable's `Config/` directory and validated before platform/native startup. `--execution-config <path>` selects an override. See the [execution guide](execution.md) for the three settings, shipped budgets, coordinator overhead and the distinction between ECS workers and synchronous Shmup/native physics.

Classic Breakout ticks run input/native physics first, then independent ball/round and brick ECS jobs, then join both before publishing. The physics engine, not an ECS movement system, owns flight integration and collisions. No world reads/writes overlap its native step; native events are fully copied/consumed before destroying bodies. Structural ECS changes occur only at exclusive boundaries. The pinned Arch query scheduler is static, so the shared host deliberately does not replace it or run nested `ParallelQuery` calls: graph-level jobs provide concurrency over disjoint archetypes instead.

`BallSimulation.StepAsync` queues ticks from any caller thread and returns that tick's immutable `SimulationSnapshot`; snapshots can be retained while work continues. Queries queue behind accepted ticks. Disposal drains accepted work before releasing native worlds, worker pools and ECS storage. `Step` is a blocking compatibility wrapper; the current input/render host joins ticks before drawing, not a requirement that gameplay or physics execute on the render thread. Host input staging remains host-thread-owned. Async I/O, further jobs and snapshot-based render overlap remain possible without changing collision ownership. Dependency graphs, tasks and retained snapshots currently allocate; the scheduler's name does not imply allocation-free ticks or a measured speedup.

## Native physics and ownership

Published **Ahwoo.BRUTAL.Box2D 2026.10.2** replaces the custom collision solver. In classic Breakout, one native world owns three static arena walls, live static brick bodies and a dynamic circle with bullet CCD. Events are consumed and deduplicated before hit bodies are destroyed with `B2Body.Dispose()`. The fixed clock, input staging and catch/aim/restart policy remain our game code. The conversion is **100 logical units per meter**, stepping at the configured fixed frequency/substep count through the dependency-job pipeline and Box2D task bridge. Each disposable session owns its simulation/world; the hidden gameplay script owns its own session. Both normal and exceptional app exits dispose these before draw-list/renderer teardown. Showcase and renderer-only smoke modes create no physics world. Snapshot state remains readable after disposal; native operations and session advances do not.

Native contacts are not analytic radius-inset guarantees: bounded checks allow **2 logical units of contact penetration plus a separately named .001 coordinate-roundoff margin**, without clamping positions. At the original explicit 120Hz/four-substep test fixture, the measured worst was 2.000179291 units over 100,000 ticks/ten shots; speed drift was .000190735 units/second. Those measurements are not a universal tolerance guarantee for every configuration. Native cast contact centers have about .5-unit slop, so post-impact paths are not the old exact time-of-impact trajectories. Corners need not yield a combined two-axis normal; initial overlap/zero-normal or ambiguous casts can legitimately have no hit. The presentation's secondary full-radius cast uses a **one-unit query-only separation skin** along the first native normal; it does not move the ball or shrink collision geometry, and clips the fixed short reflected leg when the next obstruction is available. Executable checks for these behaviors live in `tests/Runtime/Simulation/`.

Published native assets cover **win-x64, linux-x64 and osx-arm64 only**; only Windows x64 runtime behavior is verified here. Native worlds are explicitly drained and disposed through their execution host, with no finalizer or shared global world. Shared world creation/destruction is serialized to protect native global allocation state; separate worlds may advance concurrently.

## How this differs from Unity

- `src/App/Program.cs` owns initialization, OS event processing and shutdown; no Unity player lifecycle.
- GLFW creates the window, not graphics. The main thread polls and renders; minimization waits briefly for events. The host session uses a synchronous accumulator with the shared configured fixed frequency and catch-up limit; input edges apply only on the first tick, not once per render or catch-up tick.
- Vulkan acquires an image, records a render pass and ordered indexed draws, submits and presents. A fence protects command/upload reuse; semaphores coordinate acquisition/presentation.
- `BallSimulation.Step` is the small explicit equivalent of gameplay `FixedUpdate`; state is plain data, not a GameObject/MonoBehaviour. Input snapshots are the equivalent of sampled player controls, and `BallSandbox.Build` is a state-to-draw-list presentation pass. There are no per-ball tasks or awaited frame continuations.
- BRUTAL supplies framework facilities; Breakout owns its scene/entity/loading behavior.

## Shmup native simulation and pools

Native intervals resolve entries and wall expiry chronologically, deduplicating contact/sweep facts without merging separate reentries. Brick contact takes precedence only within the same interval; a later brick cannot rescue an already expired ball.

The shipped capacities retain 512 ball slots and 2048 brick slots: 2560 Arch entities and 2562 native bodies including the two walls. Each brick body retains four convex fixture slots; unused slots are filtered out. The default pool therefore has 8706 fixed native shapes, with no fixture/body churn on reuse. Saturation drops new spawns (with separate ball/brick counters), without a deferred burst. Reused lives reset HP, contact state and wall streaks; slot IDs include life generations. Immutable snapshot arrays still allocate, so pooling is not a claim of allocation-free ticks. For both bounce and piercing, native interval counts derive from configured speed, descent and ball radius; settings requiring more than 4096 intervals per tick are rejected before allocation. Smaller balls/higher speeds therefore trade CPU time for contact fidelity. The native solver handles collision response, with ball speed restored to its configured magnitude after each native interval. Shmup simulation remains independent of input, rendering and ImGui.

Collision bookkeeping follows observed logical pairs, not every reserved ball/brick combination. Sparse interval/tick lists clear only marked lookup cells; active bodies drive native queries, and ECS damage reads only actual hit pairs. Contact-buffer ordering, compound seam deduplication, later reentries and wall-expiry chronology remain intact. Pool capacities still reserve the same bodies/fixtures, but idle slots no longer multiply pair traversal. One-pass pool publication and immutable snapshot allocation remain; this is not an allocation-free or capacity-independent claim for the whole tick.

## Input and prototype reference

Classic Breakout rules reference the Unity `Projectile.cs`, `ProjectileFactory.cs` and `GameSettings-Breakout.asset`: bottom-third catch zone, leave-zone plus contact, top/side walls, limited spawns and bounce expiry. No paddle, progression, damage scaling, drag or level/editor framework. Input uses standardized GLFW mappings; polling can miss complete edges or disconnect/reconnect between frames. Automated input tests use synthetic snapshots; see [test coverage limits](validation.md#coverage-limits).

- The configured logical canvas uniformly fits the physical framebuffer with centered letterboxing. Mouse coordinates convert from logical-window units through framebuffer DPI and fit margins, then aim from the ball center. Zero-size/nonfinite/letterbox targets are ignored.
